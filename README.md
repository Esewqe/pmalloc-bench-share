# pmalloc: переносимое сравнение аллокаторов

Исходный пакет для последовательного сравнения `old` (старый pmalloc), `new` (обновлённый pmalloc), `mi3` (mimalloc 3.6.0) и `sys` (glibc из образа Ubuntu). Локальные образы автора и файлы вне этого каталога не нужны. Это инструкция воспроизведения, а не утверждение, что полный повторный эксперимент уже выполнен этим пакетом.

## Требования и распаковка

- Docker с **Linux containers**, архитектура **x86-64 / linux/amd64**; в Windows — Docker Desktop с Linux backend. Для сопоставимых измерений запускайте на x86-64 без эмуляции другой архитектуры.
- Интернет во время сборки: Ubuntu/apt, GitHub и источники, скачиваемые upstream-скриптом. После успешной сборки сеть не нужна: команды ниже запускают контейнер с `--network none`.
- Для полного набора потоков выделите Docker не менее 8 CPU и достаточно памяти. Учитывайте лимиты CPU/RAM Docker Desktop; не сравнивайте разные лимиты как один эксперимент.
- Распакуйте весь ZIP обычным архиватором, сохраняя подкаталоги. Откройте каталог `pmalloc-bench-share`, непосредственно содержащий `Dockerfile`, `run.py`, `report.py`, `preload.cpp`, `smoke.cpp`, `LICENSE-pmalloc` и `allocators/old`, `allocators/new`. Не запускайте сборку из родительского каталога.

## Windows PowerShell

Подставьте путь к распакованному каталогу; кавычки сохраняют пробелы, в том числе в `Telegram Desktop`. Все команды выполняются в этом каталоге. Сначала создаётся каталог результатов: `--mount` требует существующий источник.

```powershell
Set-Location -LiteralPath 'C:\bench\pmalloc-bench-share'
docker build --platform linux/amd64 --build-arg BUILD_JOBS=4 -t pmalloc-bench-share .
New-Item -ItemType Directory -Force -Path '.\results' | Out-Null
$Results = (Resolve-Path -LiteralPath '.\results').Path
```

Только API smoke для четырёх аллокаторов, без бенчмарков:

```powershell
docker run --rm --init --platform linux/amd64 --network none --mount "type=bind,source=$Results,target=/results" pmalloc-bench-share --smoke-only
```

Короткий запуск **настоящих upstream-нагрузок**, а не сокращённых циклов:

```powershell
docker run --rm --init --platform linux/amd64 --network none --mount "type=bind,source=$Results,target=/results" pmalloc-bench-share --threads 1 2 --runs 1 --tests cfrac cscratch
```

Полный запуск с параметрами по умолчанию (для сопоставимых измерений добавьте `--cpuset-cpus`, см. «Стабильность измерений»):

```powershell
docker run --rm --init --platform linux/amd64 --network none --mount "type=bind,source=$Results,target=/results" pmalloc-bench-share
```

## Linux shell

Замените путь на свой; кавычки также поддерживают пробелы.

```sh
cd '/path/to/pmalloc-bench-share'
docker build --platform linux/amd64 --build-arg BUILD_JOBS=4 -t pmalloc-bench-share .
mkdir -p results
RESULTS="$(pwd)/results"
```

API smoke:

```sh
docker run --rm --init --platform linux/amd64 --network none --mount "type=bind,source=$RESULTS,target=/results" pmalloc-bench-share --smoke-only
```

Короткий реальный запуск:

```sh
docker run --rm --init --platform linux/amd64 --network none --mount "type=bind,source=$RESULTS,target=/results" pmalloc-bench-share --threads 1 2 --runs 1 --tests cfrac cscratch
```

Полный запуск (про `--cpuset-cpus` см. «Стабильность измерений»):

```sh
docker run --rm --init --platform linux/amd64 --network none --mount "type=bind,source=$RESULTS,target=/results" pmalloc-bench-share
```

Контейнер запускается от root; в Linux созданные файлы результатов могут принадлежать root. `--init` ставит в контейнер минимальный init: он пересылает сигналы runner'у и собирает завершившиеся процессы. При Ctrl+C или `docker stop` runner прерывает текущий тест и записывает `status: "failed"`. Источник bind mount должен находиться на машине Docker daemon. Для удалённого daemon это не локальный каталог клиента. Официальное описание синтаксиса и ограничений: [Docker bind mounts](https://docs.docker.com/engine/storage/bind-mounts/).

## Стабильность измерений

Разброс между одинаковыми прогонами на нагруженном десктопе с Docker Desktop/WSL2 достигает десятков процентов: larson на 8 потоках с одним и тем же аллокатором дал 5.20, 7.31 и 5.23. Различия между аллокаторами часто составляют единицы процентов. Чтобы результат можно было интерпретировать:

- Закрепите контейнер за одним логическим CPU на каждое физическое ядро. Топология:

  ```sh
  docker run --rm --entrypoint lscpu pmalloc-bench-share -e=CPU,CORE,SOCKET
  ```

  Выберите по одному `CPU` из каждого `CORE` и передайте их в `docker run` перед именем образа. Например, если SMT-соседи имеют соседние номера (`0-1`, `2-3`, …): `--cpuset-cpus 0,2,4,6,8,10,12,14`. Выбранных CPU должно быть не меньше максимального `--threads`.
- Runner печатает `WARNING` и записывает `warnings` в `environment.json`, если потоков больше доступных CPU (с учётом `--cpus`) или среди разрешённых CPU есть SMT-соседи.
- В Docker Desktop/WSL2 `--cpuset-cpus` закрепляет виртуальные CPU; гипервизор может переносить их между физическими ядрами. Для окончательных измерений предпочтительнее Linux без виртуализации.
- Задавайте `--runs` кратным 4: только тогда порядок аллокаторов сбалансирован. Чтобы делать выводы о разнице в единицы процентов, используйте `--runs 8` или больше.
- Во время прогона не нагружайте машину: закройте браузеры, IDE, другие контейнеры; не запускайте несколько экземпляров бенчмарка параллельно.

## Что именно запускается

`run.py` использует исходный `bench.sh`, не меняя его команды и размеры нагрузок. Сборка suite выполняется исходным `./build-bench-env.sh bench -j=<BUILD_JOBS>`; в неё входят загрузки shbench с проверкой upstream SHA-256, PDF и Lua. Дополнительные исходники и лицензии сохраняются в образе.

По умолчанию:

- `--threads 1 2 4 8`, `--runs 4`, `--warmup 0`, `--timeout 120` (секунд на отдельный запуск).
- `--tests cfrac espresso malloc-large larson mstress rptest alloc-test cscratch cthrash glibc-thread`.
- Однопоточные тесты без параметра числа потоков (`cfrac`, `espresso`, `malloc-large`) исполняются только в группе 1 потока. Это обычные динамически слинкованные программы; LD_PRELOAD к ним применяется.
- Все четыре аллокатора проходят API smoke. Затем конфигурации выполняются последовательно; одновременных бенчмарков нет.
- Порядок аллокаторов задаётся квадратом Уильямса: прогон i каждой группы потоков использует порядок i mod 4 (`allocator_orders` в `environment.json`). За каждые 4 прогона каждый аллокатор один раз стоит на каждой позиции и ровно один раз идёт сразу после каждого другого, поэтому эффект позиции (прогрев, частота CPU) не ложится систематически на одну пару. При `--runs`, не кратном 4, баланс неполный: runner предупреждает об этом, `summary.md` это указывает.
- При успешном полном запуске: **40 конфигураций × 4 аллокатора × 4 повтора = 640 измеренных строк**, помимо четырёх smoke-проверок. Строки прогрева, если задан `--warmup`, не входят в измеренные медианы.

`alloc-test`, `cscratch` и `cthrash` при запросе нескольких потоков также запускают upstream-варианты `alloc-test1`, `cache-scratch1`, `cache-thrash1`: это однопоточные контрольные строки, а не N-поточные результаты. Они сохраняются в плоских данных, но не подменяют N-поточные строки в основных матрицах. Различайте число запрошенных потоков `requested_procs` и фактический вариант теста.

Можно задать `--output /results/my-run` для отдельного каталога результатов. Без `--output` создаётся новый подкаталог `/results` с временной меткой; на хосте он появляется внутри `results`. Для каждого запуска используйте новый каталог. Дополнительные параметры передаются после имени образа; например, `--warmup 1` или `--timeout 300`.

Завершение запуска:

- `status: "complete"` в `environment.json`, код 0 — все прогоны успешны, отчёт полный.
- `status: "incomplete"`, код 1 — часть вызовов `bench.sh` завершилась ошибкой (краш, таймаут, недостающие, лишние или некорректные строки). Runner фиксирует это в `run_status.json`, продолжает остальные прогоны и строит отчёт: конфигурации без полного набора образцов помечаются `×` и не получают отношений. Остальные строки не зависят от сбоя: каждый тест — отдельный процесс.
- `status: "failed"`, код 1 — сбой smoke, внутренняя ошибка runner'а или прерывание. Отчёт не строится; собранные данные сохраняются.

## Результаты и интерпретация

В каталоге запуска сохраняются:

- `environment.json`: параметры и сведения об окружении, версиях и исходниках;
- `raw_results.json`: отдельные запуски, фазы и исходные метрики;
- `run_status.json`: статус выполнения; проверяйте его вместе с кодом завершения контейнера;
- исходные выводы и логи upstream-команд и smoke;
- `summary.csv` и `summary.json`: плоские медианы, min/max, число образцов, RSS и отношения, включая однопоточные контрольные строки; поля `complete`, `<пара>_coarse` и `<пара>_ranges_overlap` (см. ниже);
- `summary.md`: три основные матрицы `new/old`, `new/mi3`, `old/mi3` с пометками;
- `new_over_old.csv`, `new_over_mi3.csv`, `old_over_mi3.csv` и `matrices.json`: те же матрицы в машиночитаемом виде; пустая ячейка — не запускалось, `incomplete` — неполная конфигурация.

Отношение `A/B` считается как метрика A, делённая на метрику B: меньше 1 — преимущество A, больше 1 — преимущество B. Сравнивайте только одинаковые тесты, варианты и число потоков. В исходных данных также сохраняются RSS, CPU user/system time и page faults.

Пометки в `summary.md`:

- `≈` перед отношением: диапазоны min–max двух аллокаторов пересекаются, разница не выходит за разброс между прогонами. Это описательная пометка, а не статистический тест: прогоны идут последовательно и могут иметь общий дрейф (частота CPU, фоновая нагрузка), поэтому непересекающиеся диапазоны не означают значимую разницу. Совпадающие значения считаются пересечением. При одном прогоне разброс неизвестен, и `≈` не вычисляется.
- `*` после отношения: wall time не больше 1 с; шаг GNU time (0.01 с) составляет не меньше 1% медианы, и отношение квантовано.
- `—`: тест не запускается при этом числе потоков; `×`: неполная конфигурация.

**Важно:** `time_metric_s` — именно метрика, выдаваемая upstream, а не всегда wall-clock длительность процесса. Для `larsonN` это `1e9 / ops/sec`, для `rptestN` — `2e6 / reported memory ops per CPU second`, для `glibc-thread` — `1e9 / iterations`: нормированные обратные показатели производительности. Сравнение A/B внутри одной конфигурации осмысленно; складывать эти значения между разными нагрузками или трактовать их как общую длительность нельзя. В `raw_results.json` поле `max_rss_kib` указано в KiB; в `summary.csv/json` поля `*_median_peak_rss_mib` — в MiB. Не заменяйте пропущенный или неуспешный результат нулём.

Короткие нагрузки и один повтор чувствительны к шуму. Пример с двумя тестами — проверка рабочего пути, не основание для общего вывода о скорости. Учитывайте прогрев, частоту CPU, термолимиты, планировщик и виртуализацию; см. «Стабильность измерений». `environment.json` фиксирует модель CPU, разрешённые CPU с группировкой по физическим ядрам, cgroup `cpu.max` и `memory.max`, режим transparent huge pages и, если доступен, CPU governor.

| Компонент | Зафиксированная версия |
| --- | --- |
| Ubuntu | `24.04@sha256:fe81560990fae86dc4743202b2cb4d3df98d0bcf949173cecef15ce1127ef852` |
| [mimalloc-bench](https://github.com/daanx/mimalloc-bench.git) | `198cec2701676965970e8f0012897b8da304b3f2` |
| [mimalloc](https://github.com/microsoft/mimalloc.git), 3.6.0 | `b18ab4eef383f655e760881b02eff8af02800879` |

Dockerfile скачивает эти Git-коммиты и сверяет `HEAD`; реальные значения сохраняются в `/suite/suite-commit.txt` и `/suite/mimalloc-commit.txt`. Оригинальные исходники upstream вместе с лицензиями остаются в `/suite`, mimalloc — в `/suite/extern/mi3`; лицензия pmalloc — `/opt/licenses/LICENSE-pmalloc`.

`PROVENANCE.json` в корне пакета содержит коммиты upstream и хеши обоих заголовков; копия сохраняется в образе как `/opt/PROVENANCE.json`.

Заголовки включены в ZIP как два независимых снимка. Их происхождение в этом сравнении фиксируется SHA-256 исходных байтов:

| Снимок | Файл | SHA-256 |
| --- | --- | --- |
| Старый pmalloc | `allocators/old/pmalloc_posix.hpp` | `ca20b1ee8b8484fc09059754a569c69ceeea3b25da3f70c6e1d5a43db6cd1783` |
| Обновлённый pmalloc | `allocators/new/pmalloc_posix.hpp` | `5f1b8e6b53ae822bfc84e6a58bdbe9eeae1f5ac6214a79ba36dca0412e3620ca` |

Оба pmalloc собираются из одного `preload.cpp`, с выбором неизменённого заголовка через `-I/opt/allocators/old` или `-I/opt/allocators/new`, одинаковыми флагами:

```text
-std=c++17 -O3 -DNDEBUG -fPIC -ftls-model=initial-exec -fvisibility=hidden
-fno-builtin-malloc -fno-builtin-calloc -fno-builtin-realloc -fno-builtin-free
-fno-builtin-strdup -fno-builtin-strndup -shared -pthread
```

`PM_STATS` не определяется; для pmalloc нет LTO и `-march=native`. Mimalloc собирается CMake в `Release`: `MI_BUILD_TESTS=OFF`, `MI_BUILD_OBJECT=OFF`, `MI_BUILD_STATIC=OFF`, `MI_BUILD_SHARED=ON`. Smoke собирается с `-std=c++17 -O2 -pthread -fno-builtin` и `-ldl`. Число параллельных задач **сборки** задаётся `BUILD_JOBS` (по умолчанию 4) и не означает параллельные измерения.

Shim экспортирует C-функции семейства malloc (`malloc`, `free`, `calloc`, `realloc`, `reallocarray`, `posix_memalign`, `aligned_alloc`, `memalign`, `valloc`, `pvalloc`, `malloc_usable_size`, `strdup`, `strndup`). Как glibc 2.39 и mimalloc, `aligned_alloc` принимает размер, не кратный выравниванию; smoke проверяет это вместе с `memalign`, `valloc` и `reallocarray`.

Асимметрия C++: mimalloc экспортирует собственные `operator new`/`operator delete`, включая sized delete. У pmalloc, как и у glibc, C++-нагрузки (larson, cache-scratch, cache-thrash, alloc-test) идут через `operator new` из libstdc++, который вызывает `malloc`. Проверка с прямыми переопределениями `new`/`delete` в shim не дала разницы больше разброса между прогонами (larson на 1 и 8 потоках, alloc-test1), поэтому shim оставлен только с C API. Учитывайте это при сравнении pmalloc с mimalloc.

Для сравнения других ревизий замените только нужный файл `allocators/old/pmalloc_posix.hpp` или `allocators/new/pmalloc_posix.hpp`, сохранив имя, затем повторите `docker build` и запуски выше. Docker пересоберёт слой с pmalloc. Зафиксируйте новые хеши и не выдавайте изменённые заголовки за приведённые выше снимки; runner сохраняет фактические хеши в метаданных. При изменении интерфейса заголовка может потребоваться согласованное изменение shim; простая подмена предполагает совместимый интерфейс.

Зафиксированные исходники и команды делают конфигурацию воспроизводимой, **но не гарантируют побитово одинаковый образ**: версии пакетов apt не закреплены, upstream-загрузка PDF ссылается на изменяемый URL, а Lua выбирается upstream-тегом. Доступность внешних серверов тоже влияет на сборку. Это не влияет на отсутствие сетевых зависимостей во время запуска уже собранного образа. Абсолютные времена на разных машинах и даже повторах одной машины будут отличаться; переносите выводы только с учётом окружения и разброса.

## Проверка этого пакета

Проверена сборка из указанного Ubuntu-образа без локального образа исходного стенда. Без доступа к сети выполнены:

- API smoke всех четырёх аллокаторов, включая `aligned_alloc` с размером, не кратным выравниванию, `memalign`, `valloc` и `reallocarray`;
- сбалансированный запуск `--threads 1 2 --runs 4 --tests cscratch` с `--cpuset-cpus 0,2,4,6`: 48 измерений, четыре порядка аллокаторов, `status: "complete"`, без предупреждений;
- запуск с принудительным сбоем (`--timeout 2`, cfrac длится около 3 с): cfrac помечен `×`, остальные конфигурации посчитаны, `status: "incomplete"`, код 1;
- `docker stop` во время larson: остановка за доли секунды, `status: "failed"`, прерванный тест записан в `run_status.json`;
- полный запуск с параметрами по умолчанию и `--cpuset-cpus 0,2,4,6,8,10,12,14` (AMD Ryzen 9 5950X, Docker Desktop/WSL2, по одному CPU на физическое ядро): 640 из 640 измерений, все 16 вызовов `bench.sh` успешны, `status: "complete"`, код 0, без предупреждений, около 47 минут.

Эти проверки подтверждают работоспособность стенда, а не сравнительную производительность. В полном запуске даже с закреплёнными ядрами медианный разброс (max − min) / медиана по четырём прогонам составил 16%, а отдельные выбросы — до 2.7 раза; медиана устойчива к единичному выбросу, но небольшие различия требуют больше прогонов.
